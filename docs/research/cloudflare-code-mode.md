# Cloudflare Code Mode / MCP Code Mode

Research snapshot: 2026-09-01. Sources are limited to Cloudflare documentation, Cloudflare's blog, and first-party Cloudflare repositories.

## Key conclusion

"Cloudflare Code Mode" is not one invariant tool surface. There are three related shapes in the current first-party material:

- **Generic/current agent Code Mode:** one model-facing execution tool. Connector runtimes make `codemode.search()` and `codemode.describe()` available inside that tool alongside typed connector methods ([overview](https://developers.cloudflare.com/agents/tools/codemode/)).
- **Single-tool MCP publisher:** `codeMcpServer()` replaces an existing MCP server's tools with one model-facing `code` tool. All upstream signatures are generated as TypeScript declarations and embedded in that tool's description, so discovery is front-loaded and one outer tool call can orchestrate many upstream calls.
- **Large-API MCP publisher:** `openApiMcpServer()` exposes separate `search` and `execute` tools. `search` queries a full OpenAPI document kept inside a sandbox; after its result returns to the model, a later `execute` call performs API work. This is progressive discovery, but it is normally at least two model/tool-loop steps, not search and execution inside one outer call.

Cloudflare's February 2026 launch post describes its hosted Cloudflare API MCP as exactly `search` + `execute`. The current first-party server source at commit [`75c4dbc`](https://github.com/cloudflare/mcp/tree/75c4dbc005e2ee14b937b18089a7880062264351) additionally registers a model-facing `docs` tool, so the live source surface is now `docs`, `search`, and `execute` ([registration](https://github.com/cloudflare/mcp/blob/75c4dbc005e2ee14b937b18089a7880062264351/src/server.ts#L10-L25)). Thus, **there is one execution tool in each pattern, but the large-API MCP is not a one-tool MCP server**.

## How it works

| Question | Single-tool MCP wrapper | Search + execute OpenAPI MCP |
|---|---|---|
| Model-facing tools | One outer `code` tool ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L206-L248)). | `search` and `execute` in the reusable SDK ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L434-L584)); the current hosted server also registers `docs` as noted above. |
| Discovery and TypeScript | The wrapper calls upstream `listTools()`, converts each JSON Schema to TypeScript, and substitutes the declarations into `{{types}}` in the `code` tool description ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L140-L204)). The model receives the complete generated declarations when it loads the tool; there is no runtime search phase. | Tool descriptions contain only stable TypeScript interfaces for the OpenAPI document and `codemode.spec()` / `codemode.request()`, not a generated method per endpoint ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L299-L374)). The full spec is embedded in the search sandbox and only the model-selected subset comes back ([docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/#search-and-execute)). |
| Model-loop timing | One outer `code` call can make dependent or parallel upstream calls and return a focused result. Cloudflare explicitly calls this “one outer tool call” ([docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/#single-code-tool)). | The model **first** calls `search`; after choosing an operation it calls `execute` ([docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/#search-and-execute)). These are distinct outer MCP calls separated by another model inference step. Multiple API requests can then be composed inside the one `execute` program. |
| Sandbox | Model code runs in an isolated dynamically loaded Worker. `DynamicWorkerExecutor` creates a one-shot Worker module and defaults `globalOutbound` to `null`, blocking direct network access ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/executor.ts#L484-L518), [docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/#sandbox-and-authorization-boundary)). | Same isolation. Search has no network. Execute reaches the API only through a host callback or restricted outbound proxy; credentials remain in the host ([docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/#sandbox-and-authorization-boundary), [hosted server source](https://github.com/cloudflare/mcp/blob/75c4dbc005e2ee14b937b18089a7880062264351/src/tools/execute.ts#L25-L60)). |
| Dynamic dispatch | The sandbox exposes a JavaScript `Proxy`; any property access becomes a call through a host `ToolDispatcher`. Names are sanitized and collisions rejected. The host-side function calls the upstream MCP client's `callTool({name, arguments})` ([proxy](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/executor.ts#L361-L379), [mapping and dispatch](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L164-L176)). | `codemode.request()` crosses to the trusted host callback; the host selects/authenticates the actual HTTP request ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L525-L582)). Cloudflare's hosted server instead builds `cloudflare.request()` in the isolate and restricts outbound fetch to the configured Cloudflare API hostname while injecting auth outside user code ([source](https://github.com/cloudflare/mcp/blob/75c4dbc005e2ee14b937b18089a7880062264351/src/tools/execute.ts#L25-L51)). |
| Output normalization | Upstream MCP errors become exceptions. `structuredContent` wins; otherwise all-text content is joined and JSON-parsed when possible, while mixed/binary content retains the MCP result structure ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L61-L107)). The final value is rendered as text and truncated at roughly 6,000 estimated tokens ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/mcp.ts#L23-L44)). | The returned JavaScript value is serialized to model-facing text and bounded at the same approximate budget. The hosted API adapter normalizes Cloudflare REST, GraphQL, non-JSON, and error responses inside `cloudflare.request()` ([source](https://github.com/cloudflare/mcp/blob/75c4dbc005e2ee14b937b18089a7880062264351/src/tools/execute.ts#L94-L180)). |

### Current connector runtime

Cloudflare's newer `McpConnector` is a third, closer comparison. It obtains an MCP connection's tools, derives one typed sandbox method per schema, and dispatches each method through the original `connection.client.callTool()` ([docs](https://developers.cloudflare.com/agents/tools/codemode/mcp/), [source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/connectors/mcp.ts#L95-L143)). The one execution tool also provides in-sandbox `codemode.search()` and `codemode.describe()` ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/proxy-tool.ts#L455-L481)). Mechanically, a program can consume discovery results and dynamically call methods during one sandbox execution. However, the default tool instructions say to run a “discovery pass first” for a connector not yet used, then describe returns TypeScript declarations ([source](https://github.com/cloudflare/agents/blob/b40bc5bbbfb96151baf7c524834cae27bcae0b6a/packages/codemode/src/proxy-tool.ts#L564-L578)); when the model needs those declarations to author the real program, that expected workflow takes a later inference/execution.

## Comparison with this repository

This repository is closest to Cloudflare's current connector runtime, while borrowing properties from both MCP publishing patterns:

- Like the single-tool wrapper, Pi exposes exactly one model-facing tool, `mcp_execute` ([`src/index.ts`](../../src/index.ts)). Unlike Cloudflare's wrapper, it does **not** inject every upstream signature into that tool description.
- Like Cloudflare's connector runtime, it uses progressive search + describe inside one model-facing executor. This repository makes the expected phase boundary more explicit: one discovery execution must combine search + describe, and the next `mcp_execute` performs orchestration ([`src/codemode/tool-runtime.ts`](../../src/codemode/tool-runtime.ts)). Compared with Cloudflare's hosted API MCP, it keeps a constant **one-tool outer surface**, searches a normalized MCP tool catalog rather than raw OpenAPI operations, and adds an explicit describe stage returning exact callable signatures.
- Dispatch is analogous: a dynamic namespace resolves an exact runtime path and the trusted host authorizes then calls the underlying MCP client ([`src/mcp/codemode-adapter.ts`](../../src/mcp/codemode-adapter.ts)). This repository additionally makes authorization per child MCP call explicit and confines code in a restricted interpreter with no ambient Worker APIs, rather than a dynamically loaded Worker with optional routed outbound access.
- Result handling is closely aligned: both prefer `structuredContent`, parse JSON text when possible, and turn MCP errors into exceptions. This repository is stricter for rich content: it projects images/audio as omitted metadata and omits binary resource blobs, then applies a 50 KiB model-facing bound ([`src/mcp/result-projector.ts`](../../src/mcp/result-projector.ts), [`src/mcp/execution-projector.ts`](../../src/mcp/execution-projector.ts)).

## MCP 2026-07-28 implications

The newest MCP revision does **not** eliminate the discovery round trip by itself. It has no standard tool search/describe or discover-and-execute operation: `tools/list` still returns descriptors and `tools/call` still invokes an exact name; `server/discover` reports protocol capabilities, not the tool catalog ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [server discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover)). The protocol does not let a model rewrite an already-running program after reading an unknown signature. The current Cloudflare connector prompt reaches the same practical boundary by telling the model to run a discovery pass first.

Relevant changes:

- `tools/list` is paginated, deterministically ordered, and cacheable with `ttlMs` and `cacheScope`; changes arrive through an opted-in `subscriptions/listen` stream ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [release summary](https://blog.modelcontextprotocol.io/posts/2026-07-28/#list-results-are-cacheable)). This repository already follows pagination, but its disk cache uses a fixed seven-day age and does not consume server cache hints or the new subscription stream.
- Tool schemas now default to full JSON Schema 2020-12. `outputSchema` plus `structuredContent` gives clients a typed, validateable result boundary ([tool results](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#structured-content)). This repository already prefers `structuredContent` and carries `outputSchema`; a v2 migration should preserve strict output validation and `$ref` handling rather than degrading unknown schemas to permissive objects.
- Tool results can return `resource_link` handles, while `resources/read` is separately cacheable ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#resource-links), [resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#reading-resources)). This is directly useful for token containment: Code Mode should be able to dereference, filter, and aggregate linked resources inside the sandbox instead of returning a URI to the outer model and forcing another visible step.
- Multi Round-Trip Requests let a downstream tool return `input_required`, after which the client fulfills elicitation/sampling requests and retries the original call ([release summary](https://blog.modelcontextprotocol.io/posts/2026-07-28/#multi-round-trip-requests-mrtr), [tool flow](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#input-required-tool-results)). This improves approvals and missing-input handling, but it is still a protocol round trip. Sampling could request a nested model generation, but sampling is deprecated in this revision and new implementations are told not to adopt it ([deprecations](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)).
- Tasks are now an opt-in extension for durable, long-running work, not a way to hide ordinary discovery from the model ([Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview)). Completion only covers prompt arguments and resource-template arguments, not tool search ([completion](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/completion#reference-types)). Neither solves this repository's discovery-token issue.

This repository currently depends on `@modelcontextprotocol/sdk` v1, which targets the 2025-era protocol. The official TypeScript SDK v2 is the stable line for MCP 2026-07-28, and adopting the new revision is an explicit architectural migration rather than only an import rewrite ([v2 roadmap](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/ROADMAP.md), [migration guide](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28)).

### Recommended improvement shape

1. **Immediately shrink the fallback discovery result.** The current context projection preserves the complete discovery program, search results, descriptions, and details during the orchestration inference; it only compacts them after a later orchestration succeeds. For the very next inference, project a synthetic block containing only deduplicated exact signatures plus the catalog snapshot ID. Keep full details in the stored transcript/audit record, not the provider context. This retains the necessary information while removing most outside tokens.
2. **Add query-conditioned pre-injection for the common one-call path.** Before the provider inference, search the existing catalog with the latest user request and inject only the top few exact signatures into Code Mode instructions. The model can then make its first `mcp_execute` call the real orchestration. Keep the current progressive flow as a miss/fallback. This is host-side retrieval rather than “everything inside Code Mode,” but it is the smallest reliable way to avoid the discovery turn without another model.
3. **Keep large data inside Code Mode.** Add authorized internal resource operations (including dereferencing returned `resource_link`s) so a program can read, filter, join, and summarize resource contents before returning. Preserve `structuredContent` as the primary value, validate it against `outputSchema`, and suppress duplicate compatibility text inside the sandbox projection.
4. **Add a best-effort one-execution dynamic-call path.** An exact-path operation such as `$codemode.call({ path, input })` lets one program search, describe, and invoke when it already knows or can safely construct the input. It does not solve arbitrary unknown schemas: the already-generated program still lacks the semantic mapping from the user's intent to newly discovered required fields. Fall back to the signature-only second inference when needed.
5. **If one outer call is a hard requirement for every unknown tool, add an internal planner/compiler.** Change the outer contract toward `mcp_execute({ goal, knownInputs })`; inside the trusted host, search and describe, ask a host-owned model to compile a restricted program against only those signatures, then execute it and return only the final projection. Use a direct provider/host API rather than newly adopting deprecated MCP sampling. Record the discovered signatures, generated program, child calls, approvals, and catalog snapshot for audit/replay. This truly minimizes outer-context tokens, but adds model cost, latency, and a second-model trust boundary.
6. **Migrate protocol plumbing separately.** Move to the TypeScript SDK v2, honor `ttlMs`/`cacheScope`, invalidate via `subscriptions/listen`, support downstream `input_required`, and retain deterministic catalog snapshots. These changes improve freshness, correctness, and reconnect cost; they should not be sold as the mechanism that removes model-visible discovery.

The smallest faithful next slice is therefore **signature-only projection of fresh discovery results**, followed by **query-conditioned signature pre-injection**. The stronger “one outer call for every unknown tool” goal requires an explicit decision about nested model inference.
